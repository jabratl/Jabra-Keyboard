0) HOW TO WORK WITH THIS USER (follow these)
  - Reply in BANGLISH (Bangla written in English letters). User is NOT a coder: simple words, step-by-step.
    (The user sometimes writes full English; then answer in the language of the user's LATEST message. In the v0.1.1 session the user wrote English.)
  - Before coding: read HANDOFF/CHANGELOG, say in ~5 lines what you understood, state the task in 2-3 lines,
    ask at most ONE question, otherwise write assumptions. Plan max 5 lines, then build.
  - RULE 0: never break/rename/slow any existing feature, setting, storage key, build flow. No "clean up/refactor"
    unless asked. If a new change breaks something old, it is a bug: fix it yourself.
  - PATCH, do not rewrite files. One version = one topic. Find ROOT CAUSE before fixing; grep for the same bug elsewhere.
  - New code in separate file/module, only a tiny hook in old code; wrap in try/catch; old behaviour = automatic fallback;
    ON/OFF switch where possible; never change meaning of old keys/settings.
  - Risky things (site/API/platform dependent): max 3 stages (best, one alternative, old feature). Stage 2 only if
    session < 85%. If unsure and cannot test -> write "NOT tested".
  - New permission/network/tracking: ASK first. No secrets in code. Confirm before deleting/overwriting user data.
  - Run what can be run here (syntax, tests) and show result. Never say "works" for what was not run on a phone.
  - Output: version bump, CHANGELOG entry (WHY, what changed, what BROKE, NOT tested, files), HANDOFF update,
    zip with ONLY changed/new files at exact paths (check nothing was lost vs previous version).
    Final reply <= 10 lines + Banglish checklist ("which screen, do what, see what").
  - Session limit: after ~85% no new sub-task; at ~90% stop, give files + HANDOFF + 1 line "what I did / what is left".
